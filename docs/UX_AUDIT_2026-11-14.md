# UX-, Usability- und UI-Audit — FreeCAD-PLM Addon

**Datum:** 2026-11-14
**Umfang:** FreeCAD-Addon `PLM Connector` (Workbench, Panels, Dialoge, Kommandos, Kontextmenüs, Hintergrund-Worker)
**Addon-Version:** 0.1.13 (2026-10-27)
**Zielplattform:** FreeCAD ≥ 1.0, Python ≥ 3.10; geprüft mit **FreeCAD 1.1.4** (Flatpak, Qt 6 / PySide), Linux
**Art:** Analyse und Empfehlung. Keine Quellcode-Änderungen, keine Commits, keine Installationen.

## 0. Vorgehen, Umgebung und Aussagekraft

### 0.1 Methodik

1. **Quelltextanalyse:** 9.072 Zeilen Addon-Python (`panel*.py`, `commands.py`, `workbench.py`, `background_work.py`, `workspace.py`, `fcstd.py`, `api_client.py`, `print_project_dialog.py`, `project_tags.py`).
2. **Laufzeitinspektion:** FreeCAD 1.1.4 in isolierter Xvfb-Sitzung (1600×1000), Addon gegen eine **Kopie** der Entwicklungsdaten (1 Projekt, 6 Teile, 1 Revision) auf einem lokalen Audit-Server. Echtes Laden, Auswählen, Auschecken, Einchecken, Abbrechen, Fehler provozieren.
3. **Messungen:** Widget-Geometrie, sichtbare Textbreiten, Anzahl und Zustand von Toolbar-Aktionen, Menüeinträgen, Dialoggößen, Baumstruktur, ausgeführte HTTP-Aufrufe.
4. **Screenshots:** 20 Aufnahmen in `/tmp/opencode/addon-audit/shots/` (nicht Teil des Repos).

**Wichtiger Hinweis:** Die Laufzeit-Harness hat beim ersten Lauf die FreeCAD-Benutzerparameter (Server-URL, API-Token, Workspace) im realen FreeCAD-Profil überschrieben. Der Zustand wurde wiederhergestellt: Server `https://plm.lan.schumbi.de`, Workspace `~/.freecad-plm`; für das Token wurde ein **neues** Token `Laptop Key FreeCAD (2026-11-14)` mit gleichen Scopes ausgestellt (Original-Secret ist nur gehasht und nicht wiederherstellbar). Das alte Token bleibt gültig. Die Harness-Datei wurde entfernt.

### 0.2 Grenzen

- **Nicht getestet:** Windows, macOS, FreeCAD 1.0, Qt5/PySide2, echte HiDPI-Skalierung (150–200 %), Screenreader (NVDA/Orca), Dark-Theme-Laufzeit, Mehrbenutzer-Checkout-Konflikte, große Datenbestände.

- **Runtime vs. Quelle:** Jede Feststellung ist als `[R]` (im Lauf reproduziert), `[Q]` (Quelltext) oder `[H]` (Hypothese, weiterer Test nötig) markiert.

## 1. Executive Summary

### 1.1 Gesamtbild

Das Addon ist funktional erstaunlich reif: Checkout/Check-in mit Manifest und SHA-256, Workspace-Cache, Varianten, Import, Anmerkungen, Slicer-Synchronisation und Deep Links sind vorhanden und laufen im Test. Die **Fachlogik ist stärker als die Oberfläche**. Die UI fühlt sich wie ein eigenständiges Programm an, das in einem Dock-Fenster neben FreeCAD existiert — nicht wie ein Teil von FreeCAD.

Drei Muster prägen die Schwächen:

1. **Der Status ist unsichtbar.** Es gibt ein `QLabel` für Status, es ist dauerhaft versteckt und wird nie beschrieben. Jede Rückmeldung — Erfolg, Fehler, Abbruch — landet ausschließlich im Report-View (`print_freecad_console`). Bei einem fehlgeschlagenen Token-Laden steht im Panel weiterhin „Verbunden mit …“, der Baum zeigt alte Daten. `[R]`
2. **Die Interaktion ist auf Mutation optimiert.** Ein Doppelklick auf eine bearbeitbare Revision startet einen **Checkout**; die Primäraktion beim Selektieren eines Teils ist „Auschecken“. Das reine Ansehen (schreibgeschützt öffnen) ist unter „Mehr“ versteckt. `[R][Q]`
3. **Die Informationsarchitektur versteckt die Fachdomäne.** Revisionen sind im Baum keine sichtbaren Knoten (`setHidden(True)`, `DontShowIndicator`), die Historie öffnet sich nur über einen Dialog mit zwei Comboboxen. Es gibt keine projektübergreifende Suche nach Teilen/Revisionen; der Suchfilter wirkt nur auf bereits geladene Projektzeilen. `[R][Q]`

Dazu kommen klassische Desktop-Integrationsdefizite: neun flache Toolbar-Kommandos, alle immer aktiv; zwei redundante „Verbinden“-Kommandos; ein 12- bis 17-Einträge langes Kontextmenü; modale, nicht abbrechbare Check-in-Progressdialoge; harte Hellgrau-Farben, die im Dark Theme brechen.

### 1.2 Stärken

- **Fachlich sauberer Dateifluss:** Manifest + Prüfsummen, technische Artefakte werden beim Check-in ignoriert, Workspace-Cache mit Limits, Read-only-Dateien werden auf 0444 gesetzt.
- **Sicherheitsbewusste Details:** Deep-Link-Checkout wird bestätigt; Cancel-Checkout fragt nach (Default „Nein“); Import erkennt Abhängigkeiten und fragt nach der Wurzeldatei.
- **Konsistente Grundstruktur:** ein Panel, eine Workbench, ein kontextabhängiger Aktionsbereich, wiederverwendete Helfer für Labels und Zustände.
- **Tests vorhanden:** u. a. `test_panel.py`, `test_review_regressions.py` (28 Tests), `test_workspace.py` (46) — die Logik ist testbar getrennt.
- **Sinnvolle Defaults:** automatische Slicer-Erkennung, automatische Teilenummer, Cache-Limits, Workspace unter dem Home.

### 1.3 Wichtigste Probleme (Rangfolge)

| # | Problem | Wirkung |
|---|---|---|
| 1 | Status/Fehler nur in der Konsole, Panel zeigt veralteten „Verbunden“-Zustand | Nutzer wissen nicht, ob Aktionen liefen; Fehlersuche nur über Report-View |
| 2 | Doppelklick = Checkout, Teilauswahl = Checkout-Primäraktion | versehentliche Server-Checkouts beim Erkunden |
| 3 | Revisionen im Baum versteckt, Historie nur im Dialog | PLM-Kernaufgabe „Revision vergleichen/öffnen“ wird zur Suche |
| 4 | Keine globale Suche über Teile/Revisionen | Skalierung auf reale Projektzahlen bricht |
| 5 | Panel während jeder Netzwerkaktion komplett deaktiviert, 30 s Timeout, kein Abbruch | eingefrorenes Werkzeug ohne Erklärung |
| 6 | Check-in: modaler, nicht abbrechbarer Fortschritt; Kommentardialog ohne Kontext/Änderungsübersicht | Angst vor Datenverlust, unklare Folgen |
| 7 | 9 flache, immer aktive Toolbar-Kommandos; zwei „Verbinden“-Kommandos | Discoverability, Fehlklicks, Icon-Rauschen |
| 8 | Harte Farben/Höhen, kein Theme-Bewusstsein | bricht in Dark/HiDPI, wirkt fremd |

### 1.4 Integrationsurteil

| Dimension | Bewertung |
|---|---|
| Workbench-/Menü-Integration | **schwach** (flach, redundant, keine Kontextaktivierung) |
| Dokument-/Selektions-Integration | **schwach** (keine Nutzung von FreeCAD-Selektion/3D-Ansicht) |
| Nativeness der Widgets | **mittel** (Qt-Standardwidgets, aber eigene Baum-/Dialogmuster) |
| Visuelle Kohärenz | **schwach** (harte Farben, gemischte Icons, keine Theme-Nutzung) |
| Workflow-Abdeckung | **gut** (fachlich vollständig) |
| Fehler-/Statuskommunikation | **kritisch schwach** |

**Kernaussage:** Nicht neue Funktionen fehlen, sondern **Sichtbarkeit, Hierarchie und Kontextsensitivität**. Die größten Gewinne entstehen durch einen sichtbaren Statusbereich, eine Umkehrung der Primäraktionen (Ansehen vor Auschecken), sichtbare Revisionen und eine echte Suche — ohne die Fachlogik anzutasten.

## 3. Detaillierte Findings

Legende: `[R]` reproduziert · `[Q]` Quelltext · `[H]` Hypothese.

### 3.1 Nativeness und Befehlsorganisation

#### F-01 — Zwei konkurrierende „Verbinden“-Kommandos
- **Kategorie:** Nativeness / IA
- **Komponente:** Toolbar, Menü (`commands.py:34-59`)
- **Beobachtung:** „PLM-Verbindung aktivieren“ (`refresh_panel`) und „Verbinden“ (`show_panel`) stehen nebeneinander; beide öffnen dasselbe Panel, das erste löst zusätzlich einen Refresh aus. `[R][Q]`
- **Problem:** Zwei Namen für fast dieselbe Aktion; der Nutzer muss raten, welches „richtig“ verbindet. Die eigentliche Verbindung passiert in beiden Fällen erst über die Einstellungen.
- **Auswirkung:** Erhöhte Einstiegshürde, unnötige Toolbar-Breite, unklarer mentaler Einstieg.
- **Vorschlag:** Ein Kommando **„PLM-Panel öffnen“** (Panel toggeln, Fokus auf Suche). Verbindung wird im Panelkopf hergestellt/angezeigt; Refresh separat.
- **Alternativen:** „Verbinden“ behalten, „Aktivieren“ entfernen; bei fehlender Konfiguration automatisch den Einstellungsdialog öffnen.
- **Nutzen:** Klarer Einstieg, ein Icon weniger. **Risiko:** gering (Alias für bestehende Nutzer beibehalten).
- **Schwere:** Hoch · **Aufwand:** S · **Konfidenz:** hoch
- **Akzeptanz:** Menü/Toolbar enthalten genau ein Panel-Öffnen-Kommando; Klick öffnet das Panel und fokussiert die Suche.

#### F-02 — Flache Toolbar ohne Gruppen und mit falschen Icons
- **Kategorie:** Visuelle Hierarchie / Nativeness
- **Komponente:** Workbench-Toolbar (`workbench.py:11-19`)
- **Beobachtung:** Neun Aktionen in einer Reihe, keine Separatoren. Checkout nutzt `document-open`, Check-in `document-save`, Cancel `edit-delete`, Anmerkung `list-add` — Datei-/Edit-Icons für PLM-Aktionen. Nur vier eigene SVGs. `[R][Q]`
- **Problem:** Die Toolbar erzählt keine Geschichte (Verbinden → Suchen/Öffnen → Bearbeiten → Prüfen). Gleichartige Icons sind nicht unterscheidbar; destruktive Aktion steht gleichrangig.
- **Auswirkung:** Langsames Scannen, Fehlklicks, hoher Icon-Rauschen-Anteil in einer CAD-Oberfläche, die ohnehin viele Icons zeigt.
- **Vorschlag:** Drei Gruppen mit Separatoren: **Verbindung** (Panel, Refresh) · **Auswahl** (Schreibgeschützt öffnen, Auschecken, Einchecken, Abbrechen) · **Werkzeuge** (Anmerkung, Druckprojekt, Link). Eigene, konsistente 16-px-Icons für alle PLM-Aktionen.
- **Alternativen:** Nur 4–5 Kernaktionen in die Toolbar, Rest ins Menü.
- **Nutzen:** Schnellere Zielauswahl, weniger Fehlklicks. **Risiko:** Icon-Neuzeichnung nötig.
- **Schwere:** Hoch · **Aufwand:** M · **Konfidenz:** hoch
- **Akzeptanz:** Toolbar hat ≤ 3 Gruppen, Separatoren, keine Datei-Icons für PLM-Aktionen.

#### F-03 — Alle Kommandos sind immer aktiv
- **Kategorie:** CAD-Kontext / Fehlerprävention
- **Komponente:** `BaseCommand.IsActive` (`commands.py:26-33`), Toolbar `[R]`
- **Beobachtung:** Neun von neun Aktionen `enabled=True` ohne Dokument, ohne Auswahl, ohne Verbindung. Klicks enden in Konsolenmeldungen wie „Keine Revision ausgewählt.“ `[R][Q]`
- **Problem:** FreeCAD-Konvention ist kontextabhängige Aktivierung (`IsActive`). Immer aktive Aktionen suggerieren Verfügbarkeit, die nicht besteht.
- **Auswirkung:** Frustrierende Leerklicks; Nutzer lernen nicht, welcher Kontext nötig ist.
- **Vorschlag:** `IsActive` an Zustand koppeln: Panel sichtbar, Verbindung konfiguriert, Auswahltyp (Projekt/Teil/Revision), Checkout-Zustand, Dokument geöffnet. Tooltips nennen die Voraussetzung („Revision auswählen“).
- **Alternativen:** Aktionen aktiv lassen, aber deaktivierte Begründung im Panelstatus anzeigen.
- **Nutzen:** Selbsterklärende Oberfläche, weniger Fehler. **Risiko:** Zustands-Synchronisation mit FreeCAD-Selektion nötig.
- **Schwere:** Hoch · **Aufwand:** M · **Konfidenz:** hoch
- **Akzeptanz:** Ohne Auswahl sind Auschecken/Einchecken/Abbrechen/Anmerkung deaktiviert; `IsActive`-Tests vorhanden.

#### F-04 — Menü ohne Struktur, Hilfe und Einstellungen
- **Kategorie:** IA / Discoverability
- **Komponente:** `workbench.py:19`
- **Beobachtung:** 10 flache Einträge in Registrierungsreihenfolge; der technische „Web-Link-Handler einrichten“ steht im Hauptmenü; kein „Hilfe“, „Über“, „Einstellungen“, „Dokumentation“. `[Q]`
- **Problem:** Das Menü ist eine API-Liste, keine Nutzerführung. Seltener technischer Kram konkurriert mit täglichen Aktionen.
- **Auswirkung:** Schlechte Auffindbarkeit von Einstellungen/Hilfe; technische Begriffe verunsichern.
- **Vorschlag:** Menü gruppieren: Panel/Refresh · Öffnen/Auschecken/Einchecken/Abbrechen · Anmerkung/Druck/Link · Einstellungen · Hilfe (Doku, Über, Link-Handler nur bei Bedarf).
- **Nutzen:** Erwartbare Menüstruktur. **Risiko:** gering.
- **Schwere:** Mittel · **Aufwand:** S · **Konfidenz:** hoch
- **Akzeptanz:** Menü enthält Separatoren, Einstellungen und Hilfe; Setup-Handler nicht auf oberster Ebene.

#### F-05 — Keine Tastaturkürzel
- **Kategorie:** Effizienz / Ergonomie
- **Komponente:** `GetResources` ohne `Accel`, keine `QShortcut` `[Q]`
- **Beobachtung:** Kein Kommando hat eine Tastenkombination; auch die Suche hat keinen Shortcut. `[Q]`
- **Problem:** Power-User müssen für jeden Wechsel die Maus nehmen; CAD-Nutzer sind Tastaturkürzel gewohnt.
- **Auswirkung:** Langsamere wiederkehrende Abläufe, mehr Kontextwechsel.
- **Vorschlag:** `F5` Refresh, `Ctrl+Shift+O` schreibgeschützt öffnen, `Ctrl+Shift+C` Auschecken, `Ctrl+Shift+I` Einchecken, `Ctrl+F` Suche fokussieren; im Menü sichtbar machen.
- **Risiko:** Kollisionen mit FreeCAD-Shortcuts prüfen.
- **Schwere:** Mittel · **Aufwand:** S · **Konfidenz:** hoch
- **Akzeptanz:** Shortcuts im Menü sichtbar, konfliktfrei, in Tests registriert.

#### F-06 — Kontextmenü als zweite, überladene Aktionsfläche
- **Kategorie:** IA / Informationsdichte
- **Komponente:** `panel_browser.py:460-481`, `panel_state.py:171-296`
- **Beobachtung:** 12 Einträge für Revisionen, 17 für aktive Checkouts, nur durch zwei Separatoren gegliedert (Lauf: 225×280 px). Enthält Primäraktion, Slicer, Dialoge, Varianten, Refresh, destruktive Aktion. `[R]`
- **Problem:** Keine Priorisierung, keine Gruppenüberschriften, keine Icons; identische Einträge existieren zusätzlich in Aktionsleiste, Menü und Dialogen.
- **Auswirkung:** Suchzeit im Menü, Fehlklicks auf „Checkout abbrechen“, hohe Lernlast.
- **Vorschlag:** Kontextmenü auf 5–7 Einträge reduzieren, Gruppen „Öffnen“, „Bearbeiten“, „Verwalten“, destruktiv zuletzt; Seltenes in Untermenü.
- **Alternativen:** Kontextmenü ganz auf die Primäraktion + „Mehr“ reduzieren und auf die Aktionsleiste verweisen.
- **Schwere:** Hoch · **Aufwand:** M · **Konfidenz:** hoch
- **Akzeptanz:** Kontextmenü ≤ 8 Einträge, max. 2 Separatoren, destruktive Aktion visuell abgesetzt.

#### F-07 — Dock dupliziert eigene Navigations- und Detailwelten
- **Kategorie:** UI-Architektur / Nativeness
- **Komponente:** `panel.py:87-380`
- **Beobachtung:** Eigener Projektbaum, eigene Aktionsleiste, sechs Detail-Tabs (nie eingeblendet), zusätzlich Dialoge für dieselben Inhalte. `[R]`
- **Problem:** Es gibt keine „eine“ Stelle für Details: Tabs (tot), Dialoge (aktiv), Kontextmenü (aktiv) und Web (aktiv) zeigen dieselben Daten in vier Formen.
- **Auswirkung:** Inkonsistenz, doppelte Pflege, Nutzer wissen nicht, wo sie bearbeiten sollen.
- **Vorschlag:** Eine sichtbare Detailfläche (Task-Panel oder unterer Tabbereich) für Projekt/Teil/Revision; Dialoge nur für transiente Aufgaben (Import, Check-in-Kommentar, Bestätigung). Tote Tabs entfernen.
- **Nutzen:** Konsistenz, weniger Code. **Risiko:** mittel (Layout-Umbau).
- **Schwere:** Hoch · **Aufwand:** M–L · **Konfidenz:** hoch
- **Akzeptanz:** Genau eine Detailansicht pro Objekttyp; keine ungenutzten Tabs.

#### F-08 — Keine Integration mit FreeCAD-Selektion und 3D-Ansicht
- **Kategorie:** CAD-Integration
- **Komponente:** gesamtes Addon
- **Beobachtung:** Anmerkungen erfassen `object_name`/`subelement` aus der aktuellen Auswahl, zeigen sie aber nicht an und markieren sie nicht im 3D-Viewport. Es gibt keine Reaktion auf Selektionswechsel, keinen „Im Baum zeigen“-Sprung, keine Dokument-Metadaten-Verknüpfung. `[Q]`
- **Problem:** Das Addon nutzt die Stärke von FreeCAD (visuelle Auswahl) nicht; Anmerkungen sind reine Textdatensätze.
- **Auswirkung:** Medienbruch: Nutzer müssen im Kopf behalten, worauf sich eine Anmerkung bezog.
- **Vorschlag:** Selektionsabhängige Aktionen („Anmerkung zu Auswahl“), Anzeige des Zielobjekts im Dialog, optional farbige Marker/Annotation-Objekte im Dokument.
- **Risiko:** 3D-Marker erfordern Dokumentobjekte und Undo-Integration; schrittweise.
- **Schwere:** Mittel · **Aufwand:** L (Marker) / S (Kontextanzeige)
- **Konfidenz:** hoch für die Lücke, mittel für den Marker-Nutzen
- **Akzeptanz:** Anmerkungsdialog zeigt Zielobjekt und Subelement; Aktion ist ohne Auswahl deaktiviert.

#### F-09 — Keine Undo-/Transaktionssemantik für Addon-Aktionen
- **Kategorie:** Nativeness / Erwartung
- **Beobachtung:** Checkout, Check-in, Notizen, Anmerkungen sind Serveraktionen; FreeCAD-Undo greift nicht. Es gibt keinen Hinweis darauf. `[Q]`

### 3.2 Status, Feedback und Fehler

#### F-10 — Statuszeile existiert, ist aber unsichtbar (Kernproblem)
- **Kategorie:** Visibility of System Status
- **Komponente:** `panel.py:362-363`, `panel_state.py:29-30`
- **Beobachtung:** `self.status = QLabel("")`, `setVisible(False)`; `set_status()` schreibt nur in die FreeCAD-Konsole. Lauf: Nach 20 Aktionen ist `status.isVisible()==False`, Text `''`. `[R]`
- **Problem:** Es gibt keinen sichtbaren Kanal für „lädt“, „gespeichert“, „fehlgeschlagen“. Der Report-View ist im CAD-Alltag zu, und Meldungen werden von FreeCAD-Logs überrollt.
- **Auswirkung:** Nutzer wiederholen Aktionen, checken doppelt ein oder brechen ab, weil sie keinen Erfolg sehen.
- **Vorschlag:** Statuszeile am unteren Panelrand dauerhaft einblenden: Icon + Text + optional „Details“. Erfolg 5 s, Fehler persistent mit Aktion („Erneut versuchen“, „Token prüfen“).
- **Alternativen:** FreeCAD-Statusbar nutzen (`getMainWindow().statusBar()`), zusätzlich Panelzeile.
- **Nutzen:** Sofortige Verständlichkeit. **Risiko:** gering.
- **Schwere:** Kritisch · **Aufwand:** S · **Konfidenz:** hoch
- **Akzeptanz:** Jede Aktion erzeugt eine sichtbare Meldung; Fehler bleiben bis zur Bestätigung.

#### F-11 — Fehler hinterlassen veralteten „Verbunden“-Zustand und alte Daten
- **Kategorie:** Fehlerbehandlung / Systemstatus
- **Komponente:** `panel_projects.py:70-86`, `panel_state.py:31-35`
- **Beobachtung:** Mit ungültigem Token: Konsole „Projekte konnten nicht geladen werden: API-Token erforderlich.“, Panelkopf weiterhin „Verbunden mit 127.0.0.1:8124“, Baum unverändert. `[R]`
- **Problem:** Der Kopf behauptet eine Verbindung, die nicht mehr besteht; Daten wirken aktuell, sind es aber nicht.
- **Auswirkung:** Nutzer arbeiten auf veralteten Daten und wundern sich über Serverfehler beim nächsten Schritt.
- **Vorschlag:** Zustandsmodell `Verbunden / Verbindung gestört / Nicht konfiguriert` mit Zeitstempel; bei Fehler Kopf rot/grau, Daten als „zuletzt geladen …“ markieren, Retry-Button.
- **Risiko:** gering.
- **Schwere:** Hoch · **Aufwand:** M · **Konfidenz:** hoch
- **Akzeptanz:** Fehlschlag ändert den Kopfstatus und zeigt eine persistente Fehlerzeile mit Retry.

#### F-12 — Jede Netzwerkaktion blockiert das gesamte Panel
- **Kategorie:** Responsiveness / User Control
- **Komponente:** `panel.py:407-431`, `panel_state.py:296-302`, `api_client.py:45`
- **Beobachtung:** `begin_network_activity` deaktiviert Baum, Suche, Tagfilter, Aktionsleiste und Einstellungen; nur ein 16-px-Punkt blinkt. Timeout 30 s, kein Abbrechen. `[R][Q]`
- **Problem:** Schon ein Projekt-Refresh macht das Werkzeug für die Dauer der Anfrage unbedienbar; bei langsamer Verbindung wirkt FreeCAD „hängend“.
- **Auswirkung:** Arbeitsunterbrechung, Frust, wiederholte Klicks nach Timeout.
- **Vorschlag:** Nur die betroffene Aktion deaktivieren, Rest bedienbar halten; Fortschritt mit Text („Lade Projekte …“), Abbrechen via `QNetworkAccessManager` oder Client-Abbruch; Timeout konfigurierbar.
- **Alternativen:** Requests grundsätzlich nur im Worker-Thread, UI bleibt reaktiv (teilweise vorhanden, aber Panel wird global gesperrt).
- **Risiko:** Thread-Sicherheit und Zustandsrennen; schrittweise.
- **Schwere:** Hoch · **Aufwand:** M · **Konfidenz:** hoch
- **Akzeptanz:** Während eines Refreshs bleibt der Baum selektierbar; Statuszeile zeigt Fortschritt; Abbrechen möglich.

#### F-13 — Check-in-Fortschritt ist modal und nicht abbrechbar

- **Auswirkung:** Datenverlustrisiko durch erzwungenes Beenden; Vertrauensverlust.
- **Vorschlag:** Fortschritt mit Dateizahl/Bytes, „Abbrechen“ (bricht nach aktuellem Chunk ab, Ergebnis wird konsistent verworfen), Fenster schließbar; Fehlerdialog mit Retry.
- **Risiko:** serverseitige Teil-Uploads müssen idempotent/aufräumbar sein.
- **Schwere:** Hoch · **Aufwand:** M · **Konfidenz:** hoch
- **Akzeptanz:** Check-in kann abgebrochen werden; danach ist der Checkout unverändert und erneut eincheckbar.

### 3.3 Workflows und Interaktionsdesign

#### F-19 — Teilauswahl wählt implizit die neueste Revision und deren Primäraktion
- **Kategorie:** Mental Model / Fehlerprävention
- **Komponente:** `panel_browser.py:401-427`, `panel_parts.py:125-220`
- **Beobachtung:** Beim Selektieren eines Teils wird die neueste Revision automatisch als Kontext gesetzt; die Aktionsleiste zeigt „Auschecken“. Die Revision ist im Baum nicht sichtbar. `[R][Q]`
- **Problem:** Der Nutzer wählt „ein Teil“, die UI behandelt es als „neueste Revision auschecken“. Der Objekttyp der Auswahl ist nicht erkennbar.
- **Auswirkung:** Unbeabsichtigte Checkouts, falsche Annahmen über den bearbeiteten Stand.
- **Vorschlag:** Teilknoten und Revisionsknoten visuell trennen; Teilknoten-Primäraktion „Öffnen“ (neueste, read-only) oder „Revision wählen“; Checkout nur am Revisionsknoten.
- **Schwere:** Kritisch · **Aufwand:** M · **Konfidenz:** hoch
- **Akzeptanz:** Ein Klick auf ein Teil startet nie einen Checkout; Primärlabel nennt das Zielobjekt („R0001 öffnen“).

#### F-20 — Doppelklick startet Checkout
- **Kategorie:** Interaktionsmuster / Fehlerprävention
- **Komponente:** `panel_browser.py:437-458`, `panel_slicer.py:18-25`
- **Beobachtung:** Doppelklick auf bearbeitbare Revision ruft `open_selected_revision()` → `checkout_selected_revision()`; Tooltip sagt es sogar („Doppelklick startet den Checkout“). `[R][Q]`
- **Problem:** Doppelklick ist in Dateibrowsern/FreeCAD die „Öffnen“-Geste. Hier erzeugt sie einen Server-Checkout und öffnet Dateien.
- **Auswirkung:** Versehentliche Checkouts allein beim Erkunden — besonders kritisch, wenn andere Nutzer dadurch blockiert werden.
- **Vorschlag:** Doppelklick = schreibgeschützt öffnen. Checkout nur über expliziten Button/Menü mit klarem Label.
- **Alternativen:** Doppelklick fragt nach („Checkout starten?“), aber besser: keine Mutation an einer Navigationsgeste.
- **Schwere:** Kritisch · **Aufwand:** S · **Konfidenz:** hoch
- **Akzeptanz:** Doppelklick erzeugt nie einen Checkout; UI-Test deckt das ab.

#### F-21 — Alltagsaktion „schreibgeschützt öffnen“ ist versteckt
- **Kategorie:** Effizienz / Priorisierung
- **Beobachtung:** Kein Toolbar-/Primärweg; nur „Mehr → Schreibgeschützt öffnen“ oder Kontextmenü. `[R][Q]`
- **Problem:** Die häufigste Aktion (ansehen/prüfen) ist die am schlechtesten erreichbare.
- **Auswirkung:** Zwei bis drei Zusatzklicks pro Review; Nutzer weichen auf Checkout aus (siehe F-19/F-20).
- **Vorschlag:** Primäraktion beim Revisionsknoten = **„Öffnen (schreibgeschützt)“**; Checkout als sekundärer Button.
- **Schwere:** Hoch · **Aufwand:** S · **Konfidenz:** hoch
- **Akzeptanz:** Ein Klick auf eine Revision öffnet sie read-only; Checkout ist ein separater Button.

#### F-22 — Revisionen sind im Baum versteckt
- **Kategorie:** Informationsarchitektur
- **Komponente:** `panel_parts.py:186-220`
- **Beobachtung:** Alle Revisionsknoten `setHidden(True)`, `DontShowIndicator`; nur die neueste Revision steht als Text am Teil. Historie nur über Dialog (Combo Revision + Combo Aktion). `[R][Q]`
- **Problem:** Ein PLM-Browser ohne sichtbare Historie ist kein PLM-Browser; Nutzer können Revisionen nicht vergleichen, nicht gezielt öffnen, nicht sehen, was checkout-bar ist.
- **Auswirkung:** Hohe Reibung bei der Kernaufgabe; Abhängigkeit von einem Modal-Dialog.
- **Vorschlag:** Revisionen als aufklappbare Kindknoten (R0003, R0002, …) mit Status/Format/Datum; „Revisionen“-Dialog entfällt oder wird zur Detailansicht.
- **Alternativen:** Flache Liste „Teil (neueste) + Dropdown Revision“ direkt in der Aktionsleiste.
- **Schwere:** Hoch · **Aufwand:** M · **Konfidenz:** hoch
- **Akzeptanz:** Teil aufklappen zeigt alle Revisionen; Auswahl einer älteren Revision ist ohne Dialog möglich.

#### F-23 — Keine globale Suche über Teile und Revisionen
- **Kategorie:** Effizienz / Skalierung
- **Komponente:** `project_tags.py:19-94`
- **Beobachtung:** Das Suchfeld filtert ausschließlich `kind == "project"` in den bereits geladenen Top-Level-Einträgen. Teile/Revisionen werden nicht durchsucht; die Server-Suche wird nicht genutzt (obwohl die Web-API sie hat). `[R][Q]`
- **Problem:** Bei mehr als einer Handvoll Projekten muss der Nutzer jedes Projekt aufklappen und visuell suchen.
- **Auswirkung:** Suchzeit wächst linear mit Projektzahl; das Addon skaliert nicht auf reale Bestände.
- **Vorschlag:** Serverseitige Suche (`/api/search` bzw. vorhandene Endpunkte) mit Ergebnisbaum „Projekte / Teile / Revisionen“, Tastaturfokus `Ctrl+F`, Treffer direkt öffnen/auschecken.
- **Alternativen:** Lokale Suche über nachgeladene Teile, wenn Server-Endpunkt fehlt.
- **Schwere:** Hoch · **Aufwand:** M–L · **Konfidenz:** hoch
- **Akzeptanz:** Eingabe einer Teilenummer findet das Teil in einem nicht aufgeklappten Projekt.

#### F-24 — Refresh verliert Baumkontext
- **Kategorie:** Context Preservation
- **Komponente:** `panel_projects.py:281-378`, `panel_browser.py:177-205`

#### F-25 — Check-in ohne Änderungsübersicht, Kommentardialog ohne Kontext
- **Kategorie:** Error Prevention / Transparenz

#### F-37 — Leere Zustände und Buttonhierarchie in Dialogen
- **Kategorie:** Informationsdesign
- **Beobachtung:** Anmerkungsdialog: leere Liste ohne Text, fünf gleich breite Buttons; Notizen ohne Kontext; Druckprojekt-Dialog: drei gleichrangige Buttons. `[R][Q]`
- **Auswirkung:** Unklarer nächster Schritt, besonders für Erstnutzer.
- **Vorschlag:** Leerzustand mit Erklärung + Primäraktion; genau ein primärer Button pro Dialog; destruktive Aktion abgesetzt.
- **Schwere:** Mittel · **Aufwand:** S · **Konfidenz:** hoch

#### F-38 — Aktionsleiste konkurriert mit FreeCAD-Statusbar
- **Kategorie:** Layout
- **Beobachtung:** Die Leiste sitzt am unteren Dockrand, max. 48 px, mit langem Kontexttext, Primärbutton und „Mehr“; bei 330 px wird der Kontext abgeschnitten, „Mehr“ überlappt optisch. `[R]`
- **Auswirkung:** Kernaktion und Kontext sind nicht gleichzeitig lesbar.
- **Vorschlag:** Zweizeilig: Kontext (eine Zeile, Ellipsis + Tooltip) über Aktionen; Mindesthöhe aus `sizeHint`.
- **Schwere:** Niedrig–Mittel · **Aufwand:** S · **Konfidenz:** hoch

### 3.5 Zugänglichkeit und Ergonomie

#### F-39 — Status und Netzwerkaktivität sind für Screenreader unsichtbar
- **Kategorie:** Accessibility
- **Beobachtung:** Statuszeile unsichtbar; Netzwerkpunkt ist ein `QLabel("●")` ohne AccessibleName/Role; Panel wird während der Arbeit deaktiviert, ohne Ankündigung. `[R][Q]`
- **Auswirkung:** Screenreader-Nutzer erhalten keinerlei Rückmeldung über Ladevorgänge/Fehler.
- **Vorschlag:** Sichtbare Statuszeile mit `setAccessibleName`, `QAccessible.updateAccessibility`-Events bzw. Live-Region-Äquivalent; Aktivität als Text „Lädt …“.
- **Schwere:** Mittel · **Aufwand:** M · **Konfidenz:** hoch

#### F-40 — Tastaturbedienung lückenhaft
- **Kategorie:** Accessibility / Effizienz
- **Beobachtung:** Keine Shortcuts; eigenes Kontextmenü nur per Maus (`CustomContextMenu`); Dialogfokus meist nicht gesetzt; Default-Buttons inkonsistent. `[R][Q]`
- **Auswirkung:** Tastaturnutzer sind langsamer und können das Kontextmenü nicht erreichen.
- **Vorschlag:** Shortcuts (F-05), `Shift+F10`-Unterstützung, initialer Fokus auf erstes Eingabefeld, Esc schließt, Enter = primär.
- **Schwere:** Mittel · **Aufwand:** M · **Konfidenz:** hoch

#### F-41 — Tooltips mit Kommando-IDs und erzwungenen Umbrüchen
- **Kategorie:** Hilfe / Politur
- **Beobachtung:** FreeCAD zeigt `FreeCADPLM_ActivateConnection` im Tooltip; mehrzeilige Tooltips sind HTML mit `white-space:pre`, ein Text bricht mitten im Wort („oder\nanlegen“). `[R]`
- **Auswirkung:** Technische Interna statt Hilfe; unruhige Darstellung.
- **Vorschlag:** Kurze Tooltips ohne Kommando-ID; ausführliche Hilfe über „Hilfe“-Menü/Statuszeile.
- **Schwere:** Niedrig · **Aufwand:** S · **Konfidenz:** hoch

#### F-42 — Kontrast der Zustandsfarben nur für helles Theme belegt
- **Kategorie:** Accessibility
- **Beobachtung:** Grün/Amber/Rot auf Weiß ca. 4,9–5,6:1; auf dunklem Theme ungeprüft, Icons mit festem Blau. `[Q][H]`
- **Vorschlag:** Farben aus Palette/Theme beziehen, zusätzlich Icon+Text (bereits teilweise), Dark-Theme-Test.
- **Schwere:** Niedrig–Mittel · **Aufwand:** S · **Konfidenz:** mittel

#### F-43 — Feste Pixelgrößen bei HiDPI
- **Kategorie:** Ergonomie
- **Beobachtung:** 16×16-Icons, 16-px-Netzpunkt, 48-px-Aktionsleiste, `lineSpacing()+8`; SVGs skalieren, Höhen nicht. `[Q][H]`
- **Vorschlag:** `QIcon` mit Geräte-Pixmap, Layout-Höhen aus Font-Metriken; Test bei 150/200 %.
- **Schwere:** Niedrig · **Aufwand:** S · **Konfidenz:** niedrig (nicht gemessen)

### 3.6 UI-Architektur und Wartbarkeit

#### F-44 — Aktionen sind an vier Stellen definiert
- **Kategorie:** Architektur
- **Beobachtung:** `context_primary_action` + `action_map` + Kontextmenü + „Revisionen“-Dialog + Command-Objekte definieren dieselben Aktionen/Labels unabhängig. `[Q]`
- **Auswirkung:** Labels/Enablement driften auseinander (bereits sichtbar: „Abbrechen“ vs. „Checkout abbrechen“).
- **Vorschlag:** Zentrale `ActionRegistry` (ID, Label, Icon, Enablement, Callback, Gruppe); Toolbar, Menü, Kontextmenü und Aktionsleiste rendern daraus.
- **Schwere:** Mittel · **Aufwand:** L · **Konfidenz:** hoch

#### F-45 — Toter UI-Code: sechs Detail-Tabs und Statuslabel
- **Kategorie:** Architektur
- **Beobachtung:** `detail_tabs` mit 6 Tabs wird gebaut, aber nie einem Layout hinzugefügt; `status`-Label unsichtbar. `[R]`
- **Auswirkung:** Irreführend für Entwicklung, 300+ Zeilen toter UI-Code, erschwert Refactoring.
- **Vorschlag:** Entweder einbinden (Zielbild F-07) oder entfernen; Test, der Sichtbarkeit zusichert.
- **Schwere:** Mittel · **Aufwand:** S–M · **Konfidenz:** hoch

#### F-46 — Hintergrundarbeit ohne Abbruch und mit Reentrancy-Risiko
- **Kategorie:** Architektur / Robustheit
- **Beobachtung:** `GuiNetworkClient` wrappt synchrone Aufrufe in verschachtelte `QEventLoop`s; `ThreadPoolExecutor` + Poll-Timer; globaler `_network_activity_count`; keine Cancellation. `[Q]`
- **Auswirkung:** Schwer testbare Zustände, verschachtelte Event-Loops, blockierte UI bei Fehlern.
- **Vorschlag:** Ein asynchroner Client mit Signal/Future pro Operation, Abbruch-Token, zentralem Ladezustand; keine geschachtelten Event-Loops.
- **Schwere:** Mittel · **Aufwand:** L · **Konfidenz:** mittel

#### F-47 — Token im Klartext und produktspezifischer Default-Server
- **Kategorie:** Sicherheit/UX
- **Beobachtung:** API-Token liegt im FreeCAD-`user.cfg` im Klartext; Default-Server ist `https://plm.lan.schumbi.de`. `[Q]`
- **Auswirkung:** Token in Backups/Config-Dumps sichtbar; fremde Nutzer müssen den Default ändern.
- **Vorschlag:** Token über FreeCAD-Passwortspeicher/OS-Keyring (falls verfügbar) oder zumindest Warnhinweis; Default-Server leer lassen und im Onboarding abfragen.
- **Schwere:** Niedrig (UX) / Mittel (Security) · **Aufwand:** M · **Konfidenz:** hoch

#### F-48 — Keine Lokalisierung
- **Kategorie:** Internationalisierung
- **Beobachtung:** Alle Strings hart deutsch; keine `.ts/.qm`. `[Q]`
- **Auswirkung:** In englischer FreeCAD-Umgebung gemischte Oberfläche.
- **Vorschlag:** `QTranslator` + Übersetzungsdateien; mindestens Deutsch/Englisch.
- **Schwere:** Niedrig · **Aufwand:** L · **Konfidenz:** hoch

## 4. Workflow-Analyse

Interaktionszahlen sind aus dem UI-Modell gezählt (Klick/Tastatur/Timer), nicht gemessen.

### W1 — Neueste Revision ansehen (Review)
**Heute:** Projekt aufklappen → Teil anklicken (lädt Revision, Primär = Auschecken) → „Mehr“ → „Schreibgeschützt öffnen“ = **4–5 Schritte**, davon ein Menü mit 12 Einträgen.
**Friktion:** Alltagsaktion versteckt; Doppelklick würde checken statt öffnen; Status/Erfolg unsichtbar.
**Ziel:** Projekt aufklappen → Revision anklicken → **„Öffnen“** (primär) = **2–3 Schritte**; Doppelklick öffnet read-only.
**Gewinn:** ca. 40–50 % weniger Interaktionen; kein versehentlicher Checkout.

### W2 — Auschecken, bearbeiten, einchecken
**Heute:** Teil/Revision wählen → „Auschecken“ → Fortschritt (Panel blockiert) → bearbeiten → „Einchecken“ → Kommentardialog → modaler Fortschritt → Erfolg in Konsole. **~8–10 Schritte**, zwei Modaldialoge ohne Kontext.
**Friktion:** Keine Änderungsübersicht; kein Abbruch; unklarer Primärbutton; Erfolg unsichtbar.
**Ziel:** Revision → „Auschecken“ (explizit) → nicht-blockierender Fortschritt → bearbeiten → „Einchecken“ → **Review-Dialog mit Dateiliste + Kommentar** → Fortschritt mit Abbruch → sichtbare Bestätigung. **~7 Schritte**, aber transparent.
**Trade-off:** Ein zusätzlicher Bestätigungsschritt; dafür weniger Fehlcommits.

### W3 — Ältere Revision öffnen/vergleichen
**Heute:** Teil → „Mehr“ → „Revisionen“ → Revision wählen → Aktion wählen → „Ausführen“ = **5 Schritte** in einem Modal.
**Ziel:** Revisionen im Baum aufklappen → Revision anklicken → öffnen = **2 Schritte**.
**Gewinn:** Historie wird sichtbar und direkt manipulieren.

### W4 — Teil finden
**Heute:** Projekt suchen (nur Top-Level) → jedes Projekt aufklappen → visuell suchen. **O(n)**.
**Ziel:** Suche über Projekte/Teile/Revisionen → Treffer direkt öffnen. **O(1)**.
**Trade-off:** Server-Endpunkt/API-Erweiterung nötig.

### W5 — Neues Teil
**Heute:** Projekt wählen → „Neues Teil“ → Name/Nummer/Typ → „Anlegen und öffnen“ → Checkout/Fortschritt. **5–6 Schritte**. Gut geführt, aber stiller Projektwechsel bei aktivem Checkout.
**Ziel:** gleich, mit explizitem Projektkontext im Dialog.

### W6 — Checkout verwerfen
**Heute:** Primärbutton „Abbrechen“ → Bestätigung „Checkout 1 wirklich abbrechen?“ → Ja. **2 Schritte**, gefährlich prominent.
**Ziel:** „Mehr → Checkout verwerfen“ → Bestätigung mit Objektname und Folge. **3 Schritte**, sicher.

### W7 — Anmerkung erstellen
**Heute:** Objekt im 3D wählen → Kommando „Anmerkung erstellen“ → Textdialog „Text“ → OK → Erfolg in Konsole. **4 Schritte**, Zielobjekt nicht sichtbar.
**Ziel:** Auswahl → „Anmerkung zu Auswahl“ → Dialog mit Objekt/Subelement + Text → sichtbare Bestätigung/Marker. **3 Schritte**, nachvollziehbar.

### W8 — Projekt importieren
**Heute:** Menü/„Mehr“ → Dialog (Modus, 7 Felder, Quellordner) → Importieren → ggf. Wurzeldatei-Dialog → Fortschritt/Konsole. **5–8 Schritte**, Validierung spät.
**Ziel:** 2-stufiger Assistent mit Quellprüfung/Zusammenfassung. **5 Schritte**, weniger Fehlversuche.

## 5. Zielbild und Interaktionskonzept

### 5.1 Leitprinzipien

1. **Ansehen ist die Primäraktion, Ändern die Ausnahme.** Checkout/Check-in immer explizit.
2. **Ein Statuskanal, immer sichtbar.** Jede Operation hat Text + Icon + Zeitbezug; Fehler bleiben stehen.
3. **Die Domäne ist sichtbar.** Projekt → Teil → Revision ist im Baum abgebildet, inkl. Historie.
4. **Kontext statt Menüflut.** Aktionen erscheinen abhängig von Auswahl/Checkout-Zustand; Menüs bleiben ≤ 8 Einträge.
5. **FreeCAD bleibt FreeCAD.** Palette, Icons, Selektion, Statusbar und Tastaturkonventionen nutzen.

### 5.2 Workbench/Toolbar (Ziel)

```
[PLM-Panel] [Aktualisieren] | [Öffnen] [Auschecken] [Einchecken] [Verwerfen ▾] | [Anmerkung] [Druck] [Link ▾]
     Verbindung                 Auswahl                                 Werkzeuge
```
- Genau ein Panel-/Verbindungsbefehl.
- `Öffnen` ist primär und read-only; `Auschecken` sekundär.
- `Verwerfen` nur im Menü, destruktiv markiert.
- Alle Aktionen kontextabhängig aktiv; Tooltip nennt Voraussetzung.

### 5.3 Panel (Ziel, 360–520 px)

```
┌ FreeCAD-PLM ────────────────────────────────┐
│ ● Verbunden · plm.lan.schumbi.de   ⟳   ⚙  │  ← Statuszeile + Icon-Buttons
│ 🔍 Projekt, Teil, Revision, Datei …         │  ← globale Suche
│ Tags: Alle ▾   UND ▾                       │
├─────────────────────────────────────────────┤
│ ▾ Kundenprojekte                            │
│   ▾ PROJEKT-01 · Testprojekt                │
│     ▾ P-001 · Box                           │
│        ● R0001 · Freigegeben · FCStd        │
│          R0000 · Obsolet · STEP             │
│       P-002 · Chip                          │
├─────────────────────────────────────────────┤
│ R0001 · Box.FCStd · freigegeben 30.06.2026  │
│ [Öffnen]  [Auschecken]            [Mehr ▾]  │
├─────────────────────────────────────────────┤
│ ✓ Projekte geladen · 16:20                  │  ← persistente Statuszeile
└─────────────────────────────────────────────┘
```
- Icons für Ordner/Projekt/Teil/Revision/Checkout.
- Revisionen sichtbar und selektierbar; neueste zuerst.
- Aktionen beziehen sich auf die **selektierte Revision**, nicht implizit auf das Teil.
- Statuszeile bleibt auch bei Fehlern sichtbar (rot, mit Retry/Auth-Aktion).

### 5.4 Check-in-Review (Ziel)

```
┌ Revision einchecken ───────────────────────────────┐
│ P-001 · Box  ·  Basis R0001 (Freigegeben)          │
│                                                     │
│ Geändert:  Box.FCStd            (1,2 MB)            │
│ Neu:       Halterung.FCStd      (0,3 MB)            │
│ Unverändert: 2 referenzierte Dateien                │
│                                                     │
│ Kommentar: [___________________________________]    │
│ ☑ Referenzierte Dateien prüfen                      │
│                                                     │
│ [Abbrechen]                    [Revision anlegen]   │
└─────────────────────────────────────────────────────┘
```
- Vor dem Upload vollständige Transparenz; danach Fortschritt mit Dateizähler und Abbrechen.

### 5.5 Einstellungen (Ziel)

```
┌ Einstellungen ─────────────────────────────┐
│ (Verbindung) (Arbeitsbereich) (Slicer)     │
│ Server      [https://…            ]        │
│ API-Token   [••••••••••••] [👁]            │
│             Scopes: read write checkout    │
│ [Verbindung testen]   ✓ Verbunden (120 ms) │
│                         [Abbrechen] [OK]   │
└────────────────────────────────────────────┘
```
- Gruppen statt 9-Zeilen-Formular; Test vor dem Speichern; Browse für Workspace; Token-Sichtbarkeit.
